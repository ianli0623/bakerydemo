# 後台帳號與密碼安全設計

## 狀態

- 日期：2026-09-02
- 狀態：使用者已核准聊天中的安全政策、架構、登入流程、資料與測試方向
- 範圍：Wagtail 後台 `/admin/`、Django 管理後台 `/django-admin/`、正式環境 HTTPS 設定及相關管理指令

## 目標

1. 新帳號及管理員重設的臨時密碼在首次登入後必須立即變更。
2. 正式環境的登入與改密碼流量一律經 HTTPS 傳輸，localhost 開發環境保留 HTTP。
3. 同一帳號連續登入失敗 5 次後鎖定 15 分鐘，跨 IP 仍累計，成功登入後清零。
4. 密碼至少 12 個字元，並同時包含英文大寫、英文小寫、數字及特殊符號。
5. 密碼最長使用 90 天，到期後必須先變更才能繼續使用後台。
6. 新密碼不得與目前及最近使用過的密碼重複；每位使用者保留最近 3 組密碼歷程。
7. 密碼及密碼歷程只保存 Django 支援的密碼雜湊，不保存明文。

## 非目標

- 不更換 Django 內建使用者模型，也不遷移既有使用者主鍵或權限。
- 不在本次加入多因素驗證、單一登入、LDAP 或外部身分提供者。
- 不為 localhost 建立或管理本機 TLS 憑證。
- 不把密碼雜湊或登入失敗明細暴露在 Wagtail 編輯介面。
- 不嘗試回推功能上線前使用過的舊密碼；既有密碼歷程只能從上線時的目前密碼開始建立。

## 現況與限制

- 專案使用 Django 內建使用者與 Wagtail 登入頁，沒有自訂 `AUTH_USER_MODEL`。
- `AUTH_PASSWORD_VALIDATORS` 已啟用相似度、最小長度、常見密碼及純數字驗證，但尚未強制大小寫、數字與特殊符號的組合。
- 正式環境已預設啟用 `SECURE_SSL_REDIRECT`、代理 HTTPS 標頭及 HSTS；仍需明確啟用安全的 session 與 CSRF Cookie。
- 測試與 localhost 開發環境刻意停用 HTTPS 重新導向。
- `reset_admin_password` 目前會直接使用 `ADMIN_PASSWORD`，而基本設定的開發預設值為 `changeme`。
- 專案目前沒有登入失敗鎖定、密碼效期、強制首次變更或密碼歷程資料。

## 選定方案

採用混合方案：使用 `django-axes` 處理登入失敗計數、鎖定及冷卻時間；新增 `bakerydemo.account_security` Django app 處理首次變更、密碼效期、複雜度、密碼歷程、共用改密碼頁與管理指令。

選擇成熟元件處理登入節流，可減少自訂安全敏感程式；專案特有的密碼政策仍維持在小型、可測試的本地模組中。Django 原生密碼驗證器保留並擴充，不修改 Wagtail 或 Django 核心程式。

## 安全政策

### 登入鎖定

- 鎖定鍵為正規化後的帳號名稱，不以 IP 作為分組條件。
- 同一帳號累積 5 次失敗即鎖定，從不同 IP 嘗試仍屬同一計數。
- 鎖定時間為 15 分鐘，時間到後自動解除。
- 成功登入後清除該帳號的失敗紀錄。
- 鎖定與一般驗證失敗使用相同的使用者訊息，不透露帳號是否存在、目前失敗次數或帳號狀態。
- 鎖定回應可使用 HTTP 429 與 `Retry-After`，但畫面文字維持一致。
- 保留受限的管理指令供緊急人工解除；不在一般 Wagtail 選單提供解鎖按鈕。

### 密碼複雜度

新密碼必須：

- 至少 12 個字元。
- 至少包含 1 個英文大寫、1 個英文小寫、1 個數字及 1 個特殊符號；特殊符號指非英文字母、非數字且非空白的字元。
- 通過 Django 既有的帳號屬性相似度、常見密碼與純數字密碼驗證。
- 通過最近 3 組密碼歷程驗證。

所有由 Wagtail、Django 管理後台、共用改密碼頁及專案管理指令設定的密碼都使用同一組驗證器。直接以未受控程式或資料庫修改密碼不屬於支援流程。

### 密碼效期與臨時密碼

- 密碼變更成功時寫入 `password_changed_at`。
- `password_changed_at` 滿 90 天即視為過期。
- 新建立帳號與任何不經共用自助改密碼流程設定的新密碼，均標示 `must_change_password=True`。
- 使用者完成共用改密碼流程後，清除強制變更旗標並重新起算 90 天。
- 功能上線時，既有帳號以資料 migration 的執行時間作為效期起算點，不會在部署當下全部被阻擋。

## 資料模型

### `UserSecurityState`

每位 Django 使用者一筆 OneToOne 安全狀態：

- `user`：指向 `settings.AUTH_USER_MODEL`。
- `must_change_password`：是否只能進入改密碼與登出流程。
- `password_changed_at`：最近一次成功設定密碼的時間。
- `created_at`、`updated_at`：維運與問題追蹤時間。

不存在狀態列時，由服務層以 `must_change_password=True`、`password_changed_at=None` 的封閉預設安全建立，避免缺資料時繞過政策。資料 migration 為現有使用者建立狀態，預設不要求立即改密碼，並把 migration 時間設為初始 `password_changed_at`。

### `PasswordHistory`

- `user`：指向 `settings.AUTH_USER_MODEL`。
- `encoded_password`：Django 產生的完整編碼密碼雜湊。
- `created_at`：該密碼開始使用的時間。

每次密碼雜湊成功變更後新增一筆，並在同一交易中只保留最近 3 筆。比對候選密碼時使用 Django 的 `check_password`；不解碼、不記錄也不輸出明文。此模型不註冊到一般 Wagtail 或 Django 管理介面。

部署資料 migration 只可把每位現有使用者的目前密碼加入第一筆歷程。因系統沒有舊資料，上線前的另外兩組密碼無法追溯；使用者後續變更後會逐步填滿 3 筆。

## 元件與責任

### `django-axes`

- 加入 app、middleware 與 authentication backend。
- 使用資料庫 handler，確保多程序部署共用失敗計數。
- 設定 `AXES_FAILURE_LIMIT=5`、15 分鐘冷卻、依 username 鎖定及成功登入後重設。
- 透過專案自己的 lockout 回應呈現通用、可翻譯的訊息。

### 密碼驗證器

- `PasswordComplexityValidator`：驗證長度與四種字元類別，回傳可翻譯的欄位錯誤。
- `PasswordHistoryValidator`：有使用者物件時比對最近 3 筆雜湊；新帳號尚無歷程時直接通過。
- 既有 Django validators 繼續啟用，最小長度明確設為 12。

### 密碼服務

集中提供一個交易式密碼變更服務：

1. 使用完整 validator 集合驗證候選密碼。
2. 確認與最近 3 組歷程不重複。
3. 呼叫 `set_password` 並保存使用者。
4. 新增密碼歷程並裁切到 3 筆。
5. 更新 `password_changed_at` 與 `must_change_password`。
6. 任一步驟失敗時回滾，避免只更新部分資料。

使用者自行完成共用改密碼流程時將 `must_change_password` 設為 false；管理員建立、重設或管理指令設定密碼時設為 true。密碼變更偵測需涵蓋 Wagtail 與 Django 使用者管理表單，避免從另一個後台入口繞過政策。

### 安全中介層

對已驗證的 staff 或 superuser 檢查：

- `must_change_password=True`；或
- `password_changed_at` 已超過 90 天。

符合任一條件時保存原始安全返回網址，並導向共用改密碼頁。允許清單只包含改密碼、登出、必要的靜態／媒體資源及錯誤處理路徑，避免重新導向迴圈。匿名登入頁仍由原登入流程處理，停用帳號仍依 Django 原生規則拒絕登入。

### 共用改密碼頁

- Wagtail `/admin/` 與 Django `/django-admin/` 登入後都使用同一個安全改密碼 view、form 與 URL。
- 表單要求目前密碼與新密碼確認，並顯示繁體中文或英文的可翻譯錯誤。
- 成功後呼叫 `update_session_auth_hash`，讓目前安全 session 保持登入。
- 完成強制變更後返回原後台入口；缺少安全返回網址時預設回 Wagtail 後台首頁。

## 登入與密碼資料流

### 登入失敗

1. Wagtail 或 Django 登入表單提交帳號與密碼。
2. HTTPS 在正式環境保護傳輸內容；Django 僅將密碼保留於處理該請求所需的記憶體中。
3. Axes authentication backend 依帳號讀取失敗紀錄。
4. 未鎖定時執行 Django 驗證；失敗則原子化增加計數。
5. 第 5 次起回傳鎖定結果與通用錯誤；15 分鐘後自動允許再次驗證。
6. 驗證成功時清除失敗紀錄並建立正常登入 session。

### 首次登入或密碼過期

1. 登入成功後，安全中介層讀取 `UserSecurityState`。
2. 若為臨時密碼或已滿 90 天，保存原入口並導向共用改密碼頁。
3. 在完成改密碼前，其他受保護後台路徑持續被導回。
4. 改密碼成功後更新歷程與狀態，再返回原入口。

### 管理員建立或重設密碼

1. Wagtail、Django 管理後台或管理指令驗證新密碼複雜度與歷程。
2. 密碼服務保存雜湊與歷程。
3. 將該帳號標示為下次登入必須修改。
4. 管理介面只顯示成功或驗證錯誤，不顯示雜湊。

## HTTPS 與 Cookie

正式環境：

- 保留預設啟用的 `SECURE_SSL_REDIRECT`。
- 保留 `SECURE_PROXY_SSL_HEADER`，由可信任的反向代理正確設定 `X-Forwarded-Proto`。
- 啟用 `SESSION_COOKIE_SECURE=True` 與 `CSRF_COOKIE_SECURE=True`。
- 保留 HSTS；HSTS 秒數可由環境變數調整。
- `WAGTAILADMIN_BASE_URL` 必須為 HTTPS。

localhost 開發與自動測試環境保留 HTTP，不設定 Secure Cookie，避免沒有本機憑證時無法登入。此例外不得沿用至 production settings。

HTTPS 保護密碼傳輸；Django password hasher 保護資料庫內的密碼。兩者用途不同，缺一不可。

## 初始管理員密碼

- `changeme` 只可作為 localhost 開發資料的預設值。
- 正式環境 system check 發現 `ADMIN_PASSWORD` 缺少、為 `changeme` 或不符合密碼政策時回報阻擋部署的錯誤。
- `reset_admin_password` 在設定前執行完整驗證，成功後標示 `must_change_password=True`。
- 指令與日誌不得輸出密碼內容。

## 錯誤與退化行為

- 帳號不存在、密碼錯誤、帳號停用或暫時鎖定：登入頁使用相同通用訊息。
- 安全狀態缺少：安全建立預設狀態；若無法建立則拒絕受保護後台操作並記錄伺服器錯誤。
- 密碼歷程資料庫寫入失敗：整個密碼變更交易回滾，舊密碼保持有效。
- 代理 HTTPS 標頭設定錯誤：正式部署檢查與健康檢查應阻止網站以 HTTP 提供登入頁。
- Axes 資料庫暫時不可用：不得無聲略過鎖定政策；登入失敗並記錄伺服器錯誤。
- 既有使用者沒有可用密碼：不建立無效歷程，仍由 Django 原生規則拒絕密碼登入。

## 管理與隱私

- Password history 不提供後台清單、搜尋、匯出或 API。
- 登入失敗紀錄僅供安全維運，沿用 Axes 資料保留與清除工具。
- 緊急解鎖指令必須指定精確帳號名稱，執行時記錄操作者可見的結果，但不顯示密碼或密碼雜湊。
- 後續若需要安全稽核頁面，應另案設計權限與個資保留期限，不在本次範圍內。

## 測試策略

### 密碼驗證

- 少於 12 字元及缺少大寫、小寫、數字、特殊符號時各自失敗。
- 常見密碼、純數字及與帳號／姓名／Email 過度相似時失敗。
- 候選密碼與最近 3 筆任一雜湊相符時失敗，第 4 筆較舊密碼可再次使用。
- 錯誤訊息支援繁體中文與英文，且不包含候選密碼。

### 登入鎖定

- 前 4 次錯誤不鎖定，第 5 次起鎖定。
- 不同 IP 對同一帳號的失敗仍累積。
- 不同帳號互不影響。
- 15 分鐘前保持鎖定，屆滿後自動解除。
- 鎖定前成功登入會清零；解除後成功登入也會清除舊紀錄。
- 不存在、停用與鎖定帳號對瀏覽器呈現相同訊息。
- Wagtail 與 Django 兩個登入入口都執行相同政策。

### 首次變更與效期

- 新帳號、Wagtail 重設、Django 重設及 `reset_admin_password` 都設定強制變更。
- 強制變更使用者只能進入改密碼、登出與必要資源。
- 89 天 23:59:59 尚未過期，90 天邊界起視為過期。
- 完成變更後旗標清除、效期重算、session 保持有效並回到原入口。
- 停用或沒有可用密碼的帳號不能利用強制變更流程取得登入權限。

### 資料一致性

- 成功變更後新增一筆歷程並只保留最近 3 筆。
- 驗證、使用者保存、歷程保存或狀態更新任一失敗時全部回滾。
- 既有帳號 migration 建立一筆目前密碼歷程與 90 天起算狀態。
- 密碼、候選密碼及雜湊不出現在一般應用日誌或表單回顯。

### HTTPS 與設定

- production settings 強制 SSL redirect、安全 session Cookie、安全 CSRF Cookie 與 HSTS。
- production system check 拒絕缺少、不安全或不符合政策的 `ADMIN_PASSWORD`。
- dev 與 test settings 不強制 HTTPS，localhost 登入測試仍可執行。

### 手動驗收

1. 從 `/admin/` 連續輸入錯誤密碼 5 次，確認通用訊息與 15 分鐘鎖定。
2. 從不同 IP 或測試代理重複同帳號嘗試，確認仍累積。
3. 建立新編輯者，使用臨時密碼登入並確認只能先改密碼。
4. 從 `/django-admin/` 重設該帳號密碼，再次確認首次變更流程。
5. 依序更換 3 組密碼，確認最近 3 組不可重複。
6. 將測試帳號最後變更時間設為 90 天前，確認登入後被導向改密碼。
7. 在 production-like HTTPS 代理環境確認 HTTP 重新導向、Secure Cookie、HSTS 與後台登入。

## 上線與回復

1. 備份資料庫並確認可還原。
2. 設定符合政策的 production `ADMIN_PASSWORD` 與 HTTPS 代理環境。
3. 安裝新依賴並執行 Django system checks。
4. 執行 schema 與 data migrations，建立安全狀態及初始密碼歷程。
5. 執行自動測試，再依手動驗收流程檢查兩個後台入口。
6. 部署後監看登入錯誤、鎖定量與 migration 錯誤，不記錄密碼內容。

若程式部署失敗，可先回復應用程式版本；資料 migration 必須提供可逆操作，移除新增的狀態與歷程表，不修改既有 `auth_user.password`。若需要回復 Axes，先停止新登入流量，再依套件 migration 與資料保留政策處理其資料表，避免在混合版本下執行驗證。

## 驗收標準

- `/admin/` 與 `/django-admin/` 都在第 5 次失敗後按帳號鎖定 15 分鐘，且不洩漏帳號狀態。
- 新帳號與管理員重設密碼後，使用者必須先完成改密碼才能使用其他後台功能。
- 密碼符合 12 字元與四種字元類別，90 天到期，且不能重複最近 3 組。
- 密碼與歷程只保存雜湊；正式環境登入及改密碼只經 HTTPS。
- 現有使用者部署後不會立即被鎖在後台外，並從部署時間起算 90 天。
- 所有密碼變更具交易一致性，失敗時舊密碼與狀態保持可用。
- Django system checks、自動測試與兩個後台入口的手動驗收全部通過。
